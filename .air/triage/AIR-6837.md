## Root-cause leads

### 1. The multi-root / multi-project window migration is the prime suspect

The exception message is literal: `IllegalStateException: Multi-window setups are not supported yet`, thrown from
`fleet.noria.ui` and called from `fleet.frontend.ui`. The Wasm/browser backend of noria drives a **single canvas** —
it has no second-window implementation. Something on the task-editor open path started asking for a second window.

AIR has been migrating to a **multi-project (multi-root) window** for months, and that work is landing right now:

| Issue | Priority / State | Signal |
|---|---|---|
| **AIR-6808** | Normal, In progress | *"Fix LSP in multiproject setup"* — **`Fixed in builds: 262.690`** |
| AIR-6699 | Critical, Verified | *"Can't resume a docker task after migration to multi-project window"* (Fix Version 262.579) |
| AIR-6589 | Critical, Verified | *"Task list is empty for cloud tasks in the multiroot ws"* |
| AIR-6616 | Normal, Verified | *"Take into account the selected root on Temp file creation"* |
| AIR-4195 | Major, Ready for test | the feature itself: *"Cannot develop multiple projects in a single window"* |

**Working hypothesis:** the multi-root migration made the frontend open (or resolve) a window **per project root**.
On the JVM desktop client that is harmless — real OS windows exist. In the Wasm client the same path hits noria's
`Multi-window setups are not supported yet` guard, aborts UI composition for the editor/chat area, and the session
then traps with `array element access out of bounds`.

That also explains the reporter's matrix cleanly: the failure follows the **client bundle only**
(262.697 client + 262.638 workspace still fails), because the offending call is entirely frontend-side.

### 2. AIR-6808 is the only tracked AIR change in the first-bad build

A YouTrack query for `project: AIR Fixed in builds: 262.68*, 262.69*` returns **exactly one** issue: **AIR-6808**,
`Fixed in builds: 262.690` — the first bad build — described as *"LSP should work per root in the multiproject setup.
Every root should be trusted separately to allow LSP to run on it."* Assignee **Daniil Drukarev**.

**This is circumstantial, not a conclusion.** `fleet-wasm-<v>.zip` is built from `ijplatform_master_AirWasmDistribution`,
so FL / IJPL / CMP commits in the 262.679 → 262.690 window are *not* covered by an AIR-only query and are equally
plausible. Treat AIR-6808 as the first thing to rule in or out, and Drukarev as the first person to ask, not as the
answer.

### 3. The second crash is probably a cascade, not a second bug

`array element access out of bounds` immediately after the `IllegalStateException` reads as the Wasm runtime trapping
on a noria composition that was left half-built. Compare **AIR-6380** (Critical, Air Web): one throw in a shared
`fleet.frontend` path took out terminal, editor *and* navigation simultaneously. Same shape. Chase the
`IllegalStateException` first; expect the trap to disappear with it.

### 4. Suggested next step

Bisect `ijplatform_master_AirWasmDistribution` between **262.679** (good) and **262.690** (bad) — the repro is 100 %
reproducible and needs no workspace-side changes, so this is cheap. Reviewing the range for changes to noria's window
management and to whatever in `fleet.frontend.ui` resolves a window/root will likely be faster than a full bisect.
