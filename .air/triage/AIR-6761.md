## Why `Major` and not `Normal`

**Calibration.** Across all 490 AIR issues created 2026-07-01 → 2026-08-11: `Normal` 413 (84.3%),
`Major` 54 (11.0%), `Critical` 22 (4.5%), `Show-stopper` 1 (0.2%). `Normal` is the project's default
and carries almost no signal; `Major` is the band AIR actually uses for "a core control path is
broken."

**Precedent — AIR triages broken interrupt paths as `Major`:**

- AIR-5715 *"Can't stop a task, agent does nothing, stop button does not work"* → **Major**
- AIR-5700 *"Ctrl-C is not working in Terminal"* → **Major**
- AIR-4015 *"Junie: don't ask permission for Air terminal tools"* → **Major**

**Why this issue clears the `Normal` bar:**

1. **100% reproducible on the primary entry point.** Every Junie session in Air Web starts with
   a first prompt. This is not an edge case reachable only by unusual navigation.
2. **No workaround.** The user must let the first turn run to completion. In the desktop client a
   Stop control exists (see AIR-3301, AIR-5715), so this is a *parity gap*, not an unbuilt feature.
3. **It is a safety property, not a convenience one.** Junie edits files and runs shell commands.
   Losing the brake on a running agent means a wrong-direction or destructive first turn cannot be
   halted. The reporter's phrasing — "much less safe and controllable" — is precise, not rhetorical.
4. **It compounds with its siblings.** AIR-6759 reports there is no Brave/Safe-style control either.
   Together: no pre-flight guardrail **and** no in-flight brake on the same turn. Neither issue alone
   looks alarming at `Normal`; the pair is the actual user-facing risk.

**Why not `Critical`/`Show-stopper`.** AIR reserves those for crashes and hard blockers —
AIR-6380 (`NoSuchElementException` crashes Air Web), AIR-5583 (chat messages invisible until stop),
AIR-3953 (Gemini 403). Here nothing crashes, no data is lost, and controls presumably return once
the first turn ends. `Major` is the correct band.

## Why Type stays `Bug`

The report bundles four missing affordances that are **not** the same kind of thing:

| Affordance | Actually a… | Evidence |
|---|---|---|
| **stop / cancel** during first turn | **Bug** — control exists elsewhere in Air, absent here | AIR-3301, AIR-5715 reference a working Stop |
| **follow-up** during first turn | **Bug** — queueing happens but is invisible | AIR-6762 (same batch), AIR-4715 |
| **edit** an already-sent prompt | **Feature** — never existed anywhere in Air | AIR-6234 filed as `Feature` |

The dominant, highest-impact element is *cannot interrupt a running agent* — a functional defect,
so `Bug` is right and the reporter's choice stands.

Not `Usability Problem`: that type is for awkward-but-working flows (AIR-3539 "remove tooltip on
hover"). A missing brake is absent functionality, not friction. Not `Feature`: the capability exists
in Junie under AIA/CLI and elsewhere in Air.

**Suggested scope cleanup for whoever picks this up:** keep AIR-6761 as the `Bug` covering
stop/cancel/follow-up on the first turn, and split "edit an already-sent prompt" out to
AIR-6234's thread — that one is a genuine `Feature` and will otherwise block this issue from
ever being closed.

### Likely root cause — hypothesis, not verified

⚠️ This run had **no access to the Air codebase** (see below), so the following is inferred from
tracker evidence only. Treat it as a starting point to disprove, not a diagnosis.

**Hypothesis: the first prompt is submitted before an agent session exists, so the chat has no
session to attach stop/edit/follow-up controls to.**

The single strongest supporting datum is AIR-6762 — *"the prompt disappears into a queue and the
user sees a blank input again"* — filed against the same flow. A queued-but-not-yet-live message
would explain all four missing affordances at once: there is no running turn to cancel, no
rendered message bubble to edit, and no session to append a follow-up to. It also explains
AIR-6764 (draft state discarded on conversation switch) as the same state-ownership problem in
the input component.

**Second, independent signal — the Junie ACP adapter is measurably less complete than the other
agents'.** AIR-6634 records, verbatim: *"Code-wise it seems Junie is the only agent not calling
`session/load` ever."* If the Junie adapter skips parts of the session lifecycle that Claude Code
and Codex implement, the cancel/interrupt path is a strong candidate for the same treatment. Worth
checking whether the Junie adapter advertises and implements session cancellation at all, and
whether Air Web gates the Stop button on a capability flag the Junie adapter never sets.

**Concrete first checks, in order:**

1. Reproduce in Air Web with Junie vs. Claude Code side by side on the *first* prompt. If Stop
   appears for Claude Code and not Junie, it is adapter capability negotiation. If it is missing
   for both, it is the Air Web chat component's queued-message state.
2. Trace where the "new task" submit path creates the agent session relative to when it renders
   the first message.
3. Check whether the desktop client has the same defect on the first prompt. If desktop is fine,
   diff the two chat input implementations rather than hunting in the agent layer.
