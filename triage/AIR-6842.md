## 3. Why Type = Feature (keep)

`Feature` is right, though it is a genuinely close call against `Usability Problem`.

**For Feature:** nothing malfunctions. The usage-limit error is detected and surfaced accurately. All
three things the reporter asks for are **net-new capability that does not exist today**:

1. automatic continuation on another available subscription/model,
2. manual switch-and-restart that *preserves review context*,
3. wait-for-reset-and-resume.

(2) and (3) in particular need new state handling — persisting review context across an agent restart,
and a scheduler for resume. That is feature work, not a fix.

**For Usability Problem:** the `Retry`-only dead end leads the user into a guaranteed failure. That is
the classic "works as designed, design traps the user" shape — exactly how AIR-3928 was classified.

**Resolution:** keep `Feature`. The dominant content of the issue is the three new recovery mechanisms.
If the team prefers to ship the cheap part first, **split** the narrow "don't offer a `Retry` that cannot
succeed — surface the reset time and the switch action instead" into its own `Usability Problem`
subtask; that is a small, independently shippable win and it is the part users will feel first.

## 5. Context for whoever picks this up

### The prerequisite: AIR-6168 (already linked, should be a `Depend`)

**AIR-6168 is the unlock, and it is already fixed** (`Ready for test`, Agent Integration). It found that
Air was sending a non-spec `session/set_model` JSON-RPC request, which spec-compliant ACP agents reject
with `-32601 Method not found`; the correct call is **`session/set_config_option` with config id
`model`**. Critically, its description names *this exact trap*:

> "If that model has hit a rate/usage limit, the conversation is trapped ('session limit reached') with
> no way to switch out."

So AIR-6168 fixed mid-session model switching **for general chat**. AIR-6842 is the same trap in the
**Review with Agent** flow. Recovery options 1 and 2 should be able to reuse that mechanism rather than
invent a new one — **start by checking whether the review flow can reach the AIR-6168 code path at all.**
That is the highest-value first question on this ticket, and it may make option (2) nearly free.

Promote the link from `Relates` to `Depends on`.

### The quota-handling cluster

This issue is one symptom of a systemic gap. Anyone fixing it should look at the cluster and consider a
meta issue:

| Issue | P | Type | What it covers |
|---|---|---|---|
| **AIR-6413** | Normal | Bug | Credits exhausted → **crashed** Codex session, provider `477`. Closest sibling: same trigger, worse outcome. **Not currently linked — add it.** |
| **AIR-3928** | Normal | Usability Problem | *No indication* quota was exhausted; spinners spin forever. Already linked. |
| **AIR-3929** | Normal | Feature | Proactive usage-limit progress bar — prevention. Already linked. |
| **AIR-6155** | **Major** | Bug | "Quota exhausted" banner shown when BYOK is used — quota *misattribution*. **Not linked — add it.** |
| AIR-4118 | Major | Bug | Codex auto-`/compact` fails on JB AI subscription. |
| AIR-5355 | Normal | Bug | Burned through JB AI credits with a BYO model selected. |

The pattern across AIR-6413, AIR-6155 and AIR-5355: **Air's accounting of "which subscription is paying
and how much is left" is unreliable on BYO-subscription setups.** That matters directly for recovery
option 1 — "continue on another available subscription" is only safe if Air can correctly enumerate which
subscriptions exist and which are actually exhausted. If AIR-6155 is unfixed, an automatic fallback risks
switching *away* from a subscription that was never out of quota. **Sequence AIR-6155 before shipping
automatic fallback**, or gate fallback behind explicit user confirmation.

### Likely root cause — hypothesis, not verified

I could not read the AIR source in this run (see below), so treat this as a starting hypothesis:

The ACP integration layer almost certainly maps a provider usage-limit response onto a **terminal run
failure** ("Agent execution finished with an error") instead of a typed, recoverable condition. Evidence:
the reported message is the raw provider string ("You've hit your usage limit. Upgrade to Pro…"), passed
through verbatim and then followed by the generic terminal error — i.e. **no classification step**. The
same signature appears in AIR-6413 (raw `477` → session crash). Once an error is terminal, the only
generic affordance the UI can offer is `Retry`, which explains the symptom exactly.

If that holds, the fix decomposes into:

1. **Classify** usage-limit / rate-limit / quota errors as a distinct recoverable error type, carrying the
   provider's reset time (already present in the message text — parse or request it).
2. **Preserve** review context (the diff, selected changes, review prompt) independently of the agent run,
   so a run can be re-driven against a different agent without rebuilding it.
3. **Offer** switch / fallback / wait-and-resume in place of the bare `Retry`, using the AIR-6168
   `session/set_config_option` path for the switch.

Step 1 is shared with AIR-6413 and AIR-3928 and is where I would spend the first commit.

### Code landmarks

From tracker references (not from the local checkout): `AcpAgentFrontend` is named in AIR-6167 as the
component where a single unhandled ACP agent event throws and freezes the transcript — that is the right
neighbourhood for ACP event/error handling. Search for the `session/set_config_option` call added by
AIR-6168 and for the string "Agent execution finished with an error".

### Cheapest useful increment

If the full feature is too big for one iteration, ship **option 3 in read-only form**: keep the run
failed, but replace bare `Retry` with the parsed reset time plus a "switch model and re-run this review"
action that carries the review context over. No scheduler, no auto-fallback, no dependency on AIR-6155 —
and it removes the guaranteed-to-fail button, which is the part the customer actually hit.
