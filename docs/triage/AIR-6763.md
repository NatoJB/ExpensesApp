## Ready-to-post comment

**Triage: Priority `Normal` (confirmed), Type `Bug` (confirmed). One correction — this is not Junie-specific.**

**Type — Bug, not a Usability Problem.** Two things here are wrong rather than merely unpolished:
the “available skills changed” notification is agent↔host protocol state leaking into the conversation
transcript, and it is labelled *“New skills:”* on every occurrence, so nothing is being diffed against
the already-known set. Skills announced on turn 3 are not new. (AIR-4810 was filed as a Usability
Problem, but that one is a different code path — dumping skill *file contents* when a skill is invoked.)

**Priority — Normal, and deliberately so, not left at the default.** Calibration against the 648
unresolved AIR issues (6 Critical / 56 Major / 576 Normal / 10 Minor):

* Not `Minor`: it hits 100% of sessions on the very first turn. In the attached screenshot a one-word
  `hi` produces a block that fills the whole viewport — the actual reply is pushed off-screen. It is also
  the first thing a new user sees, and it has now been reported independently twice, four months apart.
* Not `Major`: nothing is blocked, no data is lost, and the workaround is to scroll. In this project
  `Major` is reserved for functional blockers (AIR-5595 no Implement button, AIR-5335 TLS failure,
  AIR-4785 auth required, AIR-6458 permission prompts in full-auto).
* Compared with its sibling batch (AIR-6757 … AIR-6764), this is the most cosmetic of the set —
  AIR-6762/6764 involve apparent data loss, AIR-6761 involves loss of control. Same priority, lower
  ranking. Worth flagging as a **quick win**: the likely fix is suppressing or collapsing one
  notification, and the equivalent Claude-side noise issues are already Verified / Ready for test.

**⚠️ Scope correction — this is not a Junie bug.** AIR-4927 (*“Junie shows skills on conversation
start”*, Submitted since 2026-04-19, unassigned, no subsystem) carries a screenshot of the **identical**
`Skills update: New skills:` block in a **Gemini 3.1 Pro** session on desktop, with local cache paths
instead of container paths. The `[Junie]` prefix and `Subsystem = Air Web` will both send whoever picks
this up down the wrong path — the defect lives in Air’s shared agent-event → chat rendering layer, and it
reproduces on desktop as well as web. Suggest `Subsystem = Chat` (as on AIR-5208) and dropping the
Junie framing from the summary.

**Likely root cause.** Air renders the agent’s “available skills/commands changed” notification as a
normal assistant message instead of consuming it as internal state that feeds the slash / skills menu.
The Claude flavour of the same event is visible in AIR-5857 —
`{"type":"system","subtype":"commands_changed","commands":[{"name":…,"description":…}]}` — which
confirms two things: the host does have a dedicated path for these events, and the payload carries
`name` + `description`. So even if the block is intentional, rendering raw absolute paths
(`/workspaces/junie-agent/.junie/skills/testable-cli-views`) rather than skill names is a second,
independent defect. Three things to look at:

1. the agent-event dispatch that decides notification vs. transcript content (ACP session updates for
   Junie/Gemini; the `system`/`commands_changed` envelope for Claude, per AIR-5857);
2. whether the announced set is diffed against what the session already knows before being labelled
   “New”;
3. AIR-5723 (*“Commands, skills and subagents are provided from all tasks”*, Ready for test) — if the
   skill set legitimately grows as tasks are aggregated onto one workspace, that could be the mechanism
   by which the announcement fires repeatedly rather than once. Check whether that fix changes the
   behaviour here before writing new code.
