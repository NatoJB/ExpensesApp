### Why Major

Calibrated against the current open AIR backlog: **6 Critical / 56 Major / 581 Normal / 10 Minor**. Major is roughly the top 9% — reserved for feature-level functional outages, which this is:

- The report is a **100% failure rate of an entire advertised mode** ("has not completed even once"), not a degradation. Planned multi-step workflows are unavailable, with no workaround.
- It is **independently corroborated by three separate reporters**, so this is not a local/environment fluke:
  - AIR-5595 — "[Junie] No Implement button in Plan mode tasks" (**Major**, 2 votes) — plan file is created but the Implement button never appears.
  - AIR-5918 — "command 'plan' not supported with junie agent" (closed as **Duplicate** of AIR-5595) — Air reports plan mode as unsupported outright; a second commenter confirmed it happens regardless of agent/model.
  - AIR-4728 — "Junie in AIR not respect Plan, Ask, Code" — mode selection ignored in Air but works in WebStorm and the Junie CLI.
- Precedent in this project: the narrower instance (AIR-5595) is already Major, and AIR-3497 ("Switching from plan to auto-edit mode") is Major. AIR-6767 is the broader statement of the same breakage, so Normal is inconsistent with its own duplicates.

**Why not Critical:** Code and Ask modes still work, Air remains usable, and there is no data loss or crash — the 6 Critical slots in this project are held for blocking/data-integrity defects. That said, prior plan-mode breakages *were* escalated to Critical when they blocked the flow end-to-end (AIR-6067, AIR-5121 — both now Verified). **If plan mode is release-gating for Junie-in-Air, bump this to Critical.**

**Why Bug and not Feature:** unlike its sibling reports filed the same day (AIR-6757/6758/6759/6760 — parity gaps where a control is *missing*), this describes an existing feature that fails to function. Bug is correct.

### Likely root cause

Evidence points at **the ACP agent integration, not plan mode itself**. Air's plan flow is implemented natively for its own Claude harness — plan written to a markdown file, plan widget, then an Implement button (AIR-3726, AIR-3736, AIR-4173). For externally-connected agents that contract appears not to be wired up:

1. **Plan handoff never completes for non-native agents.** AIR-4930 ("Plan mode does not work with Gemini CLI") is the most diagnostic report in the backlog: with Gemini CLI the agent *writes the plan to a file in the JetBrains Air library directory instead of `.air`*, so Air never picks it up and no plan/Implement UI appears. The reporter got it working **only** by explicitly instructing the agent to write into `.air`. Junie's symptom (plan file created, no Implement button — AIR-5595) is the same shape. **Prime suspect: the plan-file path/contract Air advertises to ACP agents versus where those agents actually write, and the watcher that promotes a plan file to the plan widget.**
2. **Mode is not propagated over ACP.** AIR-5918 shows Air answering "plan mode is not supported" for the Junie agent, and AIR-4728 shows Plan/Ask/Code being ignored in Air while honoured in the IDE and CLI. Worth checking whether the session mode is sent on session creation only, and whether the ACP capability negotiation silently drops it for Junie.
3. **Mid-conversation entry is a known second failure path.** AIR-4969 and AIR-5597 (Answered) report that plan mode silently degrades to chat when previous messages exist; AIR-6498 is the Claude equivalent. If the reporter entered plan mode after a first message, this alone reproduces "never runs". **Worth confirming with the reporter whether the plan attempts were on a fresh session or mid-conversation** — it splits the bug in two.
4. **Silent-hang confound.** AIR-5586 (session hangs waiting for a permission prompt that never renders, in both Ask and Full Access) and AIR-6697 (no visible output for over an hour) mean a "never completes" report can also be a stuck permission gate rather than a plan-specific defect. Note AIR-6067 established that plan mode should not be requesting tool permissions at all.
