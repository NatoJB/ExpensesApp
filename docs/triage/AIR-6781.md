## 2. Likely root cause

The reported frame is only the *caller*. The exception actually originates in shared protocol-path
code, and we have the full stack from a prior report — a comment on **AIR-5761** shows the identical
exception type and message from:

```
java.lang.IllegalArgumentException: Path should start with a drive letter or a UNC share [/Users/dev/project]
    at fleet.protocol/fleet.api.ProtocolPath$Companion.windowsPath-IoAF18A(ProtocolPath.kt:254)
    at fleet.protocol/fleet.api.ProtocolPath$Companion.parsePath-gIAlu-s(ProtocolPath.kt:326)
    at fleet.protocol/fleet.api.ProtocolPath$Companion.of(ProtocolPath.kt:311)
```

So the throw site is `ProtocolPath.Companion.windowsPath` (`ProtocolPath.kt:254`), reached via
`ProtocolPath.of()` → `parsePath()`. `GitCheckpoints.withTempIndex` (`GitCheckpoints.kt:229`) is
just the first caller that happens to hand it a WSL path.

**The hypothesis:** the rejected path *is* a UNC share — but it is spelled with **forward** slashes.

```
//wsl.localhost/Ubuntu/home/jbaumann/repos/<repo>/.git/index     ← rejected
\\wsl.localhost\Ubuntu\home\jbaumann\repos\<repo>\.git\index     ← what the validator expects
```

`windowsPath()` almost certainly tests for a drive-letter prefix (`X:`) or a literal `\\` UNC
prefix, and never accepts the `//server/share` form. That matters because **git emits forward
slashes in every path it prints** — `rev-parse --absolute-git-dir`, `--git-dir`,
`--show-toplevel` all do. Any path Air derives from git's stdout for a repo opened over
`\\wsl.localhost\...` will therefore fail to parse. `withTempIndex` composes
`<gitDir>/index` and feeds it to `ProtocolPath.of(...)`, which throws before any git process runs.

**Where the fix belongs:** in `ProtocolPath`, not in `GitCheckpoints` — normalize separators and
accept `//server/share` as a valid UNC prefix. Patching the call site would leave every other
git-derived path on the same configuration broken. Note this validator has drawn blood once
already (AIR-5761, Critical, POSIX path on Windows).

**Suspected incomplete fix:** AIR-5761 was marked *Ready for test* with **Fix Version 262.132**,
and its last comment reads "it should be already fixed, I believe". The reporter here is on
**262.132.34** — i.e. *after* that fix. The 262.132 change evidently hardened one input shape but
not forward-slash UNC.

## 3. Impact — why Major and not Normal

- Per AIR-6724, *"a git checkpoint is created at the start of every agent request and gates it."*
  If checkpoint creation throws at path-parse time, **no agent task can run at all** on such a
  repo. It is a hard block on core functionality, not a degradation.
- Repository *discovery* clearly succeeded here — the code got as far as building a temp index
  path. That is a change from the earlier WSL reports (AIR-6078, AIR-6287) which died sooner with
  "No Git repository found". WSL setups are now getting *further* into the product, so more users
  will land on exactly this exception.
- Demand is real: **AIR-5811 has 23 votes** and several comments saying WSL is a hard blocker to
  adoption.
- The likely fix is small and self-contained (separator normalization in one validator), so it
  need not wait on full WSL support.

**Why not Critical:** WSL-on-Windows is not a supported configuration yet (AIR-5811 is still an
unresolved *Feature*), and there is a workaround. Of 395 open AIR bugs, only 6 (1.5%) are
Critical — that band is reserved for breakage on supported configurations. Major (42 issues, 11%)
is the right band; compare **AIR-6469** ("Stuck in Saving checkpoint", Windows, checkpoint-blocking)
which sits at Major.

**Why not plain Normal:** the two prior WSL reports were both closed Normal + duplicate, but both
were "no repo found" at discovery. This one is a distinct, independently fixable defect in shared
path infrastructure, and it fully blocks the product's main loop.

## 4. Do not close as a duplicate of AIR-5811

(e.g. `C:\repos\<repo>`) and open it from there. Checkpoint creation only fails when the repo path
is a forward-slash UNC path.
