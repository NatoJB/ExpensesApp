## Likely root cause

The decisive detail in the report is **the browser never opens**. That places the failure
*before* the OAuth handoff, in the pre-flight Code Assist lookup — not in the callback
handling. This is what separates AIR-6851 from the superficially similar AIR-4821, where
the browser *does* open and the hang happens after the redirect.

AIR-4562 captured the stack trace for exactly this pre-flight failure:

```
💥ERROR💥 google.codeassist] Failed to fetch Code Assist info
kotlinx.serialization.MissingFieldException: Field 'cloudaicompanionProject' is required
for type with serial name 'fleet.oauth.google.common.LoadCodeAssistResponse',
but it was missing at path: $
    at kotlinx.serialization.json.Json.decodeFromString(Json.kt:149)
    at fleet.oauth.google.common.GoogleCodeAssist...
```

The Gemini provider calls Google's Code Assist endpoint to resolve
`cloudaicompanionProject` *before* launching the browser. When the account has no eligible
Code Assist project, the response omits that field, deserialization throws, the exception is
swallowed, and the sign-in coroutine never proceeds to open the browser or surface an
error — producing the exact indefinite spinner reported here. Claude and OpenAI have no
equivalent pre-flight step, which is precisely why they are unaffected.

### The important nuance: this is not simply a duplicate

AIR-4562 is **fixed in build 261.573** (Fix Version 261.584). The reporter is on
**262.132.35**, which is well past that. So the AIR-4562 fix is already present and this
still reproduces. Two readings, both worth checking:

- **Most likely — unfixed sibling case.** [AIR-5416](https://youtrack.jetbrains.com/issue/AIR-5416)
  ("Code Assist did not return a Cloud AI companion project", Normal, **Submitted**,
  Subsystem `Licensing`) is the same `cloudaicompanionProject` family and is still open,
  with AIR-6035 and AIR-6442 already deduped into it. AIR-6442 was filed on build
  **262.132.21** — the same 262.132.x line as this report. The AIR-4562 fix likely made the
  *deserializer* lenient without adding a user-facing error path for the genuine
  "account has no Code Assist project" case, so the hang persists.
- **Or — a 262.x regression** of the AIR-4562 fix.

Distinguishing them is a log check, not a guess (see below).

### Adjacent factor worth ruling out

The reporter's default browser is **Safari on macOS 26.5.2**, so a silently failing browser
launch on this OS/browser combination is the obvious fallback hypothesis. Two pieces of
evidence argue against it being the primary cause:

- Of the sign-in cluster, only AIR-4562, AIR-6442 and AIR-4413 state an OS (all macOS); most
  state none. But **AIR-5264 is titled "[Windows] Gemini does not work"**, so this failure is
  not confined to macOS — which is what a Safari-specific launcher bug would predict.
- Claude and OpenAI open the browser successfully in the same installation, so the platform's
  browser-launching mechanism demonstrably works on this machine.

Still worth ruling out via the log check, which separates the two cleanly: if
`Failed to fetch Code Assist info` appears, it is the pre-flight path; if the code reaches an
"opening browser" step and nothing happens, it is the launcher.

## Suggested next steps for whoever picks this up

1. **Ask the reporter for logs** (`Help → Collect Logs`) and grep for
   `Failed to fetch Code Assist info`, `cloudaicompanionProject`, and
   `LoadCodeAssistResponse`. This single check confirms or kills the primary hypothesis and
   decides duplicate-vs-regression.
2. **Confirm account eligibility.** Ask whether the Google account has Gemini Code Assist
   for individuals enabled. AIR-6262 documents that ineligible accounts produce an endless
   auth loop — if this account is ineligible, AIR-6851 is the *silent* variant of that bug
   and the fix is a real error message, not an auth fix.
3. **Fix the swallowed exception regardless of root cause.** Whatever the trigger, an
   indefinite spinner with no timeout and no error is a defect in its own right. The
   `Sign in` action needs a timeout and a surfaced failure message. AIR-5411 ("surface
   meaningful error on archive extraction failure") is the same class of fix and sets a
   precedent.
4. **Coordinate with the Antigravity migration before investing in a deep fix.**
   [AIR-5394](https://youtrack.jetbrains.com/issue/AIR-5394) (Major, Open, `Agent Integration`)
   tracks migrating from Gemini CLI to Antigravity CLI, since Google has deprecated
   `gemini-cli` in favour of `agy`. AIR-6823 is a user hitting this same sign-in hang and
   concluding the deprecation is the cause. A rewrite of the Gemini OAuth path may be
   superseded — but the error-surfacing fix in step 3 is worth doing either way, because
   users on the current build need feedback now.
