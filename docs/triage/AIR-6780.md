## Two distinct root causes

The reporter's split is sound and worth preserving as two fixes:

**Defect 1 — completion on missing data.** `AgentRequestExecutorKt` takes the "no execution
result" branch and completes the task without first settling tool calls still open at that moment:

```
[20260728 15:15:26.952 WARN ... f.a.w.agents.AgentRequestExecutorKt]
  Agent failed to emit an execution result. Will default to success.
```

Fix shape: a reconciliation barrier before completion — settle every non-terminal tool call for
that request (`FAILED` / `CANCELLED` / a neutral *interrupted* state), then complete; or report the
task as interrupted.

**Defect 2 — replay re-creates PENDING.** After restart the same `toolCallId` is re-emitted as a
fresh `ToolCall(status=PENDING)` and no terminal `ToolCallUpdate` can ever follow. Same id, once
live and once on replay 37 minutes later:

```
14:38:51.967  ToolCall(toolCallId=toolu_011RMKhEGCU7fiXtxdmymaDt, title=Write, kind=EDIT, status=PENDING ...
15:16:28.004  ToolCall(toolCallId=toolu_011RMKhEGCU7fiXtxdmymaDt, title=Write, kind=EDIT, status=PENDING ...
```

Fix shape: replay must distinguish a *live* tool call from a *reconstructed* one and render the
latter as interrupted when it can no longer receive a terminal status.

Evidence that this is reconciliation and not rendering: a comparable `Terminal` call **in the same
chat** moves `PENDING → IN_PROGRESS → COMPLETED` correctly, and the backing Claude Code transcript
has 87 `tool_use` blocks matched by 87 `tool_result` blocks, zero pending. The agent side is clean.
