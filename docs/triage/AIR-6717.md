## Root cause — two ranked hypotheses

Verified on a live Air 262.132.34 install (Linux paths; Windows equivalents noted).

Air keeps chat history in **two separate places**:

1. **Transcripts** — `~/.claude/projects/<url-encoded-project-path>/<sessionId>.jsonl`
   (Windows: `%USERPROFILE%\.claude\projects\...`).
   These are almost certainly the reporter's "json1 files" — `.jsonl`, with a
   lowercase L misread as a 1.
2. **The index Air actually renders from** — a monolithic, version-stamped durable
   snapshot per workspace:
   `~/.config/JetBrains/Air/localStorage/<workspaceId>/workspace/db.262.132.0.json`
   (Windows: `%LOCALAPPDATA%\JetBrains\Air\localStorage\...`), alongside
   `db-versions.11.json`. Confirmed to contain entity type
   `fleet.ai.agent.claude.workspace.ClaudeSessionStateEntity:1`.

The chat list is built from (2). Nothing rebuilds (2) from (1). That is the gap the
reporter is pointing at, and they are right.

### H1 — Workspace re-identification (most likely; direct precedent in AIR-5116)

The unclean shutdown left Air unable to rebind the folder to its existing workspace, so
it minted a **new `workspaceId`** and created a fresh, empty
`localStorage/<newId>/workspace/` directory. The old directory — with every
`ClaudeSessionStateEntity` in it — is still on disk, just orphaned.

AIR-5116 documents exactly this on build 261.474.28 (`masterWorkspaceId` reassigned
after force-quit, `AgentSessionDescriptionEntity` rows orphaned). AIR-6717 would be a
recurrence on 262.132.34, which also argues the AIR-5116 fix never landed or is
incomplete.

**This hypothesis predicts the data is fully recoverable**, which matters for the reply
to the reporter.

### H2 — Truncated durable snapshot

`db.262.132.0.json` is rewritten whole. If that write is not crash-safe
(temp file → fsync → atomic rename), a power cut mid-write leaves truncated JSON.
Deserialization is all-or-nothing, so one bad byte yields an empty DB and an empty chat
list, while the `.jsonl` transcripts are untouched.

Precedent for the resilience fix: AIR-5398, "per-entry try-and-log in
`fleet/native/crates/archive`" — tolerant per-entry parsing instead of failing the
whole payload.

### Distinguishing the two — one check

Ask the reporter to list `%LOCALAPPDATA%\JetBrains\Air\localStorage\`:

- **Several workspace-id directories, an older one holding a large
  `db.262.132.0.json`** → H1. Recoverable by rebinding the folder to that workspace id.
- **Current `db.262.132.0.json` is 0 bytes or ends mid-token** → H2.

The attached `air-logs-2026-08-07-14-17.zip` should settle it: look for a JSON
deserialization exception on `db.262.132.0.json` during startup (H2), or a
"creating new workspace" / new-workspace-id line for a known-existing folder (H1).

### Related note on AIR-6502

"Recent agentic session history disappears after updating Air and OS" is the same theme
with a third trigger: the snapshot filename embeds the build version
(`db.`**`262.132.0`**`.json`), so an upgrade without a migration path looks identical to
"no history." Worth fixing together — all three cases are the same missing capability.

## Suggested fixes

1. **Recovery (what the reporter asked for).** Rebuild the chat index by scanning
   `~/.claude/projects/**/*.jsonl`. This is feasible: each transcript line carries
   `sessionId` and `timestamp`, and the directory name encodes the project path — enough
   to reconstruct list entries without the snapshot. Offer it as an explicit
   "Rescan chat history" action, not only as silent startup repair.
2. **Durability.** Make the snapshot write crash-safe (temp + fsync + atomic rename),
   or move to an append-only journal so a partial tail is discardable.
3. **Tolerance.** Per-entity try-and-log on load rather than all-or-nothing, per AIR-5398.
4. **Visibility.** When the snapshot fails to load, surface an error. Silently rendering
   an empty chat list reads as "your data is gone."
5. **Stable workspace identity.** Bind workspaces to the canonical folder path so an
   unclean shutdown cannot orphan sessions (AIR-5116).
