* `Critical` in AIR is reserved for hard blockers — AIR-6727 (Codex fully broken after
  rust-v0.147.0), AIR-6681 (Cloud git push ignores the credential helper), AIR-6365
  (Japanese IME cannot type at all). Nothing here is blocked: the answer is produced, it is
  just in the wrong language, and it is intermittent ("sometimes").
* `Major` in AIR marks a feature that is effectively unusable — AIR-5595 (no Implement
  button in Plan mode), AIR-6167 (transcript freezes on an unhandled ACP event). A language
  mismatch degrades output quality but removes no functionality, and there is a cheap
  workaround (append "answer in Russian" to the prompt, or put it in the guidelines file —
  with the caveat from JUNIE-298 that guidelines only partially work).
* `Normal` is where the rest of this reporter's `[Junie]` parity batch sits (AIR-6757,
  AIR-6758, AIR-6759, AIR-6760, AIR-6764, AIR-6767, AIR-6769, AIR-6771) and where
  comparable non-English issues sit (AIR-6497 — Ctrl+C with a Russian keyboard layout).

So: **`Normal`**. The argument for raising it later: it hits *every* non-English user of
Junie-in-Air, not an edge configuration. If the same pattern shows up for Chinese /
Japanese / Korean prompts (cf. AIR-4732 China region, AIR-6629 Korean support), it stops
being a polish item and becomes a market-reach problem worth re-scoring to `Major`.

**On `Type`:** keeping `Bug`, because the reporter observes the behaviour as *inconsistent* —

of the competing reading: upstream Junie never promised language mirroring (JUNIE-39 and
JUNIE-298 are both still **open Feature Requests**), which would make this a

### Likely root cause

This is probably **not** a Junie-specific rendering bug in Air; it looks like prompt
composition plus model non-determinism:

* Air injects its own additional system-prompt rules into ACP agent sessions, and those
  rules are authored in English — see **AIR-4037** ("Extract duplicated additional agent
  system prompt rules": the Claude ruleset was copy-pasted for ACP agents) and **AIR-4078**
  ("Run Junie session with custom guidelines (default ACP system prompt)", which documents
  `--guidelines-filename` / `JUNIE_GUIDELINES_FILENAME` as the injection mechanisms). An
  all-English system prompt wrapped around a Russian user turn leaves the output language
  undetermined — the model picks, and it picks differently per run. That is a textbook
  explanation for "sometimes".
* Nothing in the chain appears to pass the user's locale, or a "reply in the language of the
  request" instruction, down to the agent. Confirming that absence is the first code-level
  check.
* Upstream, Junie has no language selection at all: **JUNIE-39** (repro is identical —
  non-English prompt, English reply) and **JUNIE-298** (guidelines only partially fix it).
  If the conclusion is "upstream limitation", link this to JUNIE-39 and track it rather than
  fix it in Air — but Air can still mitigate on its own side by adding a language-mirroring
  rule to the shared ACP system prompt, which is a small, self-contained change.

### Where to look

* The shared / duplicated agent system-prompt rules touched by **AIR-4037** — that is where
  a "respond in the user's language" rule belongs, and fixing it there covers Claude, Codex
  and Junie at once.
* The ACP guidelines injection path described in **AIR-4078**
  (`--guidelines-filename`, `JUNIE_GUIDELINES_FILENAME`).
* Agent Integration owns the Junie session lifecycle generally — cf. **AIR-6634** (Junie is
  the only agent that never calls `session/load`), **AIR-6600** (Junie's question tool is
  not rendered in chat). Same area, same owner.
