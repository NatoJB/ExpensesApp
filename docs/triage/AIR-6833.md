## Likely root cause

The reporter's own uncertainty ("not even sure that that's the result of the web
application") is worth resolving first, and the reported symptoms actually settle it. Two
details point strongly at the **web app, not the OS**:

1. The cursor returns when it leaves the **wasm application viewport**.
2. It returns on **rapid side-to-side movement** inside the viewport.

If the OS or the browser chrome had lost the cursor, leaving the canvas would not fix it. A
cursor that is wrong *only over one DOM element* and correct everywhere else is, by
construction, that element's own `cursor` styling.

**Primary hypothesis.** Compose Multiplatform for web/wasm applies the pointer icon by
setting the CSS `cursor` property on the canvas element that hosts the app. The
pointer-icon state machine is losing its current icon and applying `none` (or a custom
cursor value the browser cannot resolve, which renders as nothing). Because the property
sits on the canvas, the browser correctly restores the default cursor the moment the pointer
exits that element — exactly the reported behaviour. Rapid movement generates a burst of
`pointermove` events, one of which re-runs the cursor-application path and repairs the
state — also exactly as reported.

**Where to look.** The cursor/pointer-icon handling in the Compose UI layer
(`androidx.compose.ui` / `fleet.noria.ui`, per the stack traces attached to AIR-5226) and its
wasm/DOM backend. **Start from the AIR-6291 fix** (landed in build `262.182`, authored by
Manuel Unterhofer) and check whether the web/wasm cursor path received the equivalent
correction, or whether it still has the pre-fix logic.

**Secondary hypotheses**, in order:

- A hover/tooltip or drag-and-drop interaction that sets a hidden or custom cursor and
  fails to restore it when the gesture is interrupted. Compare AIR-5008 (tooltips flicker)
  and AIR-5639 (menu closes on hover movement) — both are unrestored-hover-state bugs.
- A pointer-lock or pointer-capture request that is entered and not released.
- A dropped `pointerenter`/`pointerleave` pair leaving the icon state stale — consistent
  with recovery requiring a *new* stream of pointer events.

the canvas element in devtools and read its computed `cursor` value. If it is `none` or an
unresolvable `url(...)`, the primary hypothesis above is confirmed and the OS is ruled out
outright.
