**Why `Type` isn't Bug.** Nothing is broken today — the description scopes future work
(*"In case of multirepository support, we need to commit results back"*). This is a
capability gap in the cloud commit-back path, not a defect. Worth noting the filing
pattern: 14 of the reporter's 19 AIR issues are typed `Bug`, including items that are
plainly not defects (AIR-5866 *Prepare agent distribution in Docker image*, AIR-6457
*Ability to run Custom ACP agent in the Cloud*), so `Bug` here reads as a create-form
default rather than a deliberate classification. Precedent in the multi-root family:
AIR-4195 is `Task`, AIR-5502 is `Meta Issue`, AIR-4390 is `Usability Problem`. Use
`Feature` instead if this is tracked as user-facing cloud capability.

**Why `Normal` holds.** Calibration across the 60 AIR issues created 2026-08-01..17:
**50 Normal, 6 Critical, 4 Major** — Normal is the baseline, and Major/Critical are spent
on live breakage (AIR-6837 client unusable, AIR-6699 can't resume a docker task, AIR-6834
memory blowup). The closest structural analogue is AIR-5502 *Make Git-related features
aware of focused workspace root(s)* — a `Major` meta-issue whose seven subtasks
(AIR-5726 … AIR-5741) are **all `Normal`**. AIR-6841 is another leaf of that same shape.
The reporter's own history points the same way: 17 of his 19 issues are `Normal`.

**⚠️ Escalate to Major/Critical if this is already reachable in production.** Severity
hinges on one fact that could not be verified from outside: **does ORCA already check out
multiple repos for cloud workspaces?** If it does, and commit-back only handles the
first/primary repo, then agent work in the secondary repos is **silently discarded** —
silent loss of user work, which in this project has drawn `Critical` (cf. AIR-6678, where
branch reuse across worktrees/docker was Critical). If multirepo checkout is still
unshipped or behind a flag, `Normal` is correct. Whoever picks this up should settle that
question first, because it changes the priority.

**Why `Subsystem` = Git.** It is currently unset, which leaves the issue unrouted — this
is arguably the highest-value label change here. The commit-back path is git plumbing, and
recent siblings are consistently `Git`: AIR-6840, AIR-6799, AIR-6724, and notably AIR-5708
*List of agent's commits is incorrect for resumed JCP tasks*. `Agent Integration` is the
alternative if this is owned cloud-side — that is where the reporter's other cloud items
landed (AIR-6457, AIR-5866, AIR-5311).

**Likely root cause / where to look.** The shape is clear even without the sources: the
cloud task lifecycle almost certainly carries a **single repository/branch identity per
task**, and commit-back resolves one working root. Two threads to trace:

1. **ORCA's checkout step** — does it emit a *list* of checked-out roots, or a single
   root? ORCA is the Air Cloud-side orchestrator (`JetBrains/orca-workflows`; cf. AIR-6583,
   *"requires implementation on the Air Cloud and Orca side"*).
2. **The commit-back / ACP end-turn contract** — AIR-5426 *Return git start revision
   information in ACP end turn* (same reporter, Fixed) suggests revision info crosses that
   boundary as a **scalar**. That is exactly the field that has to become a per-repo
   collection, along with the matching commit/push step.

Expect the work to be: plumb a per-root collection through checkout → task state →
commit-back, then decide product behaviour for the multi-repo case (one commit per repo;
what happens when only some repos have changes; how partial push failures are reported).
