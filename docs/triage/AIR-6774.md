## What `/pull-request` actually is

`/pull-request` is a genuine **Junie CLI built-in slash command**. Its mechanics are documented
in **JUNIE-3311** ("Junie CLI `/pull-request` fails on Windows: jq quoting broken in PR fetch"),
which is the single most useful reference for implementing this:

1. User runs `/pull-request`.
2. **Junie prompts the user for a PR number** (interactive question).
3. Junie shells out via `ShellCommandRunner`:
   `gh pr view <n> --json baseRefName,headRefName --jq '.baseRefName + "\t" + .headRefName'`
4. It reads the PR's base/head branches, then starts the review.

So the command has three hard requirements, and **AIR currently satisfies none of them end-to-end.**

## Likely root causes / dependency chain

**1. ACP command surfacing (Subsystem: Chat Commands).**
Junie advertises its built-ins to the host over ACP `available_commands_update`. The
descriptions of AIR-4899 and AIR-4908 contain the exact JSON payload shape AIR consumes for
`/plan` and `/review` — start there and check whether Junie advertises `pull-request` and
whether AIR drops or fails to render it. Known defects in that same pipeline:
AIR-5857 (`Failed to parse Claude System "commands_changed"`), AIR-5903 (cache available
commands for custom ACP agents), AIR-5500 (Codex & Junie recognise file path as a command).

**2. ⚠️ Blocked by AIR-6760 — interactive questions.**
`/pull-request` cannot function without asking the user for a PR number. **AIR-6760 "[Junie]
'Junie Asks Questions' behavior is missing"** is a sibling from the very same batch. Even if the
command is surfaced correctly, it will stall at step 2 until AIR-6760 is fixed. These two should
be linked and sequenced — AIR-6760 first. (Related: AIR-5586, session hangs waiting for
permission but unable to grant.)

**3. `gh` CLI availability and auth.**
Step 3 requires the GitHub CLI installed *and* authenticated in whatever environment AIR runs
Junie in — local, worktree, Docker, or Air Cloud. AIR has a cluster of known VCS-credential
gaps that would bite here: AIR-4242 (GitHub PAT token not working), AIR-6492 (pushing a private
repo returns 403 in Air but succeeds in terminal), AIR-4875 (git credential helper prompt
corrupts Claude agent event stream), AIR-6681 (Air Cloud credential helper ignored).

## Scope problem — recommend splitting

The description says "PR/MR review **and automation** flows", which bundles three distinct
Junie surfaces with different owners. Only the first is plausibly AIR's work:

| Junie surface | What it is | AIR's stake |
|---|---|---|
| `/pull-request` CLI command | Interactive, in-session PR review (JUNIE-3311) | **In scope** — command parity, this issue |
| Junie GitHub Action | CI-side PR review / PR creation (`junie-github-action`) | Runs in CI, not in AIR — likely out of scope |
| Junie GitLab wrapper | MR code-review in GitLab CI (JUNIE-2850, JUNIE-2814, JUNIE-3763) | The "MR" half; CI-side, out of scope |

Recommend narrowing AIR-6774 to the `/pull-request` command and dropping or re-filing the CI
automation half. Worth confirming with the reporter which she meant.

Note that AIR is **not** starting from zero on PR plumbing: "Create PR" already exists for Air
Cloud (AIR-4697 GitLab, AIR-4698 Space — both Ready for test) and PR status is shown in the task
header (AIR-6478, Fixed). What's genuinely missing is the *review* half — tracked as AIR-5754
"Support PR review" (Feature, Submitted, Ekaterina Prigara). See also AIR-4487 "Introduce Merge
actions for remote scenarios" (Shelved) and AIR-5735 (Obsolete).
