## Reasoning

### Why Bug and not Feature

Both halves of the feature already exist; only the Junie→Air path between them is broken.

* **Junie already asks.** Junie's ACP integration emits clarifying questions — verified
  working against another ACP client (Zed) in AIR-6600, and the question chips render in
  AI Assistant (LLM-27618).
* **Air already has the widget.** The Questions widget shipped via AIR-3722 (*Ready for
  test*), backend wiring in AIR-4219, answer rendering in AIR-4496. It works for other
  agents today: per AIR-6600, **Codex shows the question widget and Copilot shows a listed
  set — only Junie shows nothing.**

A capability that works for three agents and fails for a fourth is a plumbing defect, not
unbuilt functionality.

### Likely root cause

AIR-3722 was scoped explicitly *"To support Claude's AskUserQuestion tool"* — the widget was
built against a **Claude/MCP tool-call shape** (`mcp__Air__ask_user_question`). Junie asks
over **ACP elicitation**, a different transport path. AIR-6600 independently reached the
same conclusion:

> "Junie ACP supports elicitation — tested in Zed." — Ekaterina Prigara
>
> "It seems like Junie started to use ACP elicitation … and our ACP client support lacks
> it." — Mikhail Chernyavsky

Two failure modes are worth separating, because they need different fixes and carry
different severity:

1. **Capability negotiation → silent skip.** If Air's ACP client does not advertise
   elicitation support during `initialize`, Junie will not ask at all. This matches the
   report's wording precisely ("the agent *doesn't clarify*", rather than "asks and nothing
   renders"). Compare DBE-26830, where a client declaring `elicitation=null` caused consent
   to be *silently* dropped.
2. **Unhandled inbound request → stall.** If the request arrives but is unhandled, the
   session stalls instead of skipping — cf. LLM-23464, where a `session/update` →
   `tool_call_update` carrying a `questions` array left the chat stuck on "Thinking", and
   AIR-5586 / AIR-4497 (widget waits for input indefinitely).

**Fastest disambiguation:** capture `AcpTransport - IN`/`OUT` traffic for a deliberately
ambiguous Junie prompt (the technique used in LLM-23464). No outbound elicitation request →
cause 1. Request present but nothing renders → cause 2. This one check decides both the fix
and the owner.

**If it reproduces in a cloud task,** there is an independent cause: AIR-6323 reports that
`mcp__Air__ask_user_question` — in fact all `mcp__Air__*` tools — are unavailable in cloud
tasks while working locally. On that surface the agent genuinely *cannot* ask.

### Why Normal and not Major

* **Consistency:** the identical defect is already triaged Normal — AIR-6600 (same root
  cause) and AIR-6323 — as are all five sibling reports filed alongside this one
  (AIR-6757, AIR-6758, AIR-6759, AIR-6761, AIR-6762).
* **Workaround exists:** front-load detail in the prompt, or use Junie in the IDE/CLI where
  the behavior works. No data loss; Junie stays usable for well-specified tasks.
* **Major is selective in AIR:** 56 of ~647 unresolved issues (~9%, against 575 Normal),
  reserved for hard blockers — AIR-5427/AIR-4785 (auth failures), AIR-5335 (TLS handshake).
  The tier above it is narrower still (6 Critical), e.g. AIR-5380 (Junie Full Access broken,
  now *Verified*).

**Escalation caveat:** Normal holds only under failure mode 1 (silent skip, degraded UX).
If investigation shows failure mode 2 — the session *hanging* on an unhandled elicitation
request, as in LLM-23464 / AIR-5586 — that is a blocking, unrecoverable state and the
cluster should be re-rated **Major**.

### Prior art — a recurring seam

`Ask User Questions` has regressed repeatedly along this same seam: AIR-3829, AIR-4036,
AIR-4433 and AIR-4653 were all closed as duplicates of AIR-3722. A regression test asserting
the elicitation round-trip **per agent** (Junie, Codex, Copilot, Claude) would likely prevent
the next recurrence — the widget passing for one agent clearly does not imply it passes for
the others.
