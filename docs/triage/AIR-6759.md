## 4. Root cause — verified: a named feature gate, set to `false` for Air

`fleet.frontend.ai.AiChatGlobalSettings` (in `fleet.frontend.jar`) declares a Boolean UI-feature attribute **`ShowAutonomySettings`**. Exactly four classes across all 549 jars reference it — the declaration, its companion, and **two writers**:

| Writer (in `fleet.ship.desktop.jar`) | Profile | Value |
|---|---|---|
| `fleet.ship.desktop.InitAppEntitiesKt` | stock Fleet app init | **`true`** (`iconst_1`) |
| `fleet.ship.desktop.air.AirShipLauncherKt` | **the Air product profile** | **`false`** (`iconst_0`) |

Verified by disassembling both call sites; the boolean is pushed immediately after `getShowAutonomySettingsAttr()`:

```
# AirShipLauncherKt
447: invokevirtual  AiChatGlobalSettings$Companion.getShowAutonomySettingsAttr:()...Attributes$Required;
450: iconst_0                     # ← false, for the Air profile
451: invokestatic   java/lang/Boolean.valueOf:(Z)Ljava/lang/Boolean;

# InitAppEntitiesKt
135: invokevirtual  AiChatGlobalSettings$Companion.getShowAutonomySettingsAttr:()...Attributes$Required;
138: iconst_1                     # ← true, stock default
```

`AirShipLauncherKt` overrides ~38 `AiChatGlobalSettings` attributes to define the Air product profile; this is one of them. **So the autonomy surface is a first-class, named, gated UI feature that Air's own launcher turns off.** Whether that was a considered product decision or an oversight is the question to put to the assignee — it is the crux of the ticket.

Nothing in this installation *reads* `getShowAutonomySettings`; the only JVM references are the declaration and the two setters. The consumer is out-of-process — consistent with the chat UI being the remote Air Web client.

## 5. The backend is already complete — what exists today (all verified)

Per-agent mode enums in `fleet.plugins.ai.protocol.jar`:

| Class | Values | Wire values |
|---|---|---|
| `...agents.junie.JunieMode` | `ASK`, `PLAN`, `FULL_ACCESS` | `ask`, `plan`, `full-access` |
| `...agents.claude.ClaudePermissionMode` | `Plan`, `Bypass`, `AcceptEdits`, `Default` | `plan`, `bypassPermissions`, `acceptEdits`, `default` |
| `...agents.gemini.GeminiPermissionMode` | `Default`, `AutoEdit`, `Yolo` | `default`, `auto_edit`, `yolo` |
| `...agents.codex.CodexPermissionMode` | `Chat`, `Agent`, `FullAccess` | `read-only`, `agent`, `agent-full-access` |
| `...agents.GenericReportablePermissionMode` | `Unknown`, `FullAccess`, `AutoEdit`, `ManualApproval`, `PlanOnly` | normalised cross-agent vocabulary |

**Junie's Brave mode is already wired in Air:**
- `fleet.ai.agent.junie.common.JunieApiCommands.getSetBraveMode()` → command id `"acp/set-brave-mode"`
- handled by `fleet.ai.agent.junie.workspace.handlers.JunieSetBraveModeApiCommandHandler`
- which sends ACP `SetSessionConfigOptionRequest(configId = "brave_mode", BoolValue)`
- constant `fleet.ai.protocol.agents.junie.JunieModesKt.BraveModeConfigId = "brave_mode"`
- helper `JunieModesKt.braveModeConfigOption(JunieMode)` emits `BoolValue(mode == JunieMode.FULL_ACCESS)`
- generic sibling: `AcpApiCommands.getSetSessionMode()` → `"acp/set-session-mode"`

**A picker's data model already exists**, carrying display strings:

```kotlin
AgentModelConfiguration.Agent.PermissionMode(
    id: AgentPermissionModeId,
    name: String,          // display label
    description: String,   // display description
    isJcpDefault: Boolean)
```

converted for the client by `fleet.ai.workspace.acp.AcpSessionConfigOptionsKt.toPermissionModeState(...)` → ACP `SessionModeState` — sitting directly beside `toModelState(...)` → `SessionModelState`, which **does** have a shipped picker.

**The asymmetry, verified:** `fleet.frontend.ai.AiFrontendActionIds` contains `"ai/select-model"` and `"ai/toggle-model-selector"`. A scan of all 549 jars for `"ai/select-permission-mode"` returns **zero hits**. `fleet.frontend.documentation.json` has zero matches for `autonom`, `permission`, `approv`, or `brave`.

**Telemetry already treats mode as a per-prompt user choice** — `BundledMetadata_FLT.json` records, on `userPromptSubmitted`:

```json
"model"           : [ "{regexp:(claude|anthropic-claude)-…}" ],
"permission_mode" : [ "{enum:FullAccess|PlanOnly|AutoEdit|ManualApproval|Unknown}" ],
"thinking_level"  : [ "{enum:…}" ]
```

You do not add a per-prompt FUS dimension for a value the user cannot vary.

**Enforcement is real**, not decorative — `fleet.ai.agent.claude.workspace.WithClaudeKt` shells out with `--permission-mode {plan|bypassPermissions|acceptEdits|default}`, `--dangerously-skip-permissions`, `--permission-prompt-tool mcp__Air__permission-tool`, `--allowedTools`/`--disallowedTools`. Mode also drives Air's own MCP sandbox via `fleet.ai.common.mcp.AgentPermissions(sandbox, autoAllowMcp)` / `AgentSandbox(write: None|Workspace|Full, network: Boolean)` and the `JuniePermissionsUpdater` / `Claude…` / `Gemini…` / `Codex…` family. Per-request approval copy lives inline in `PermissionToolKt` ("Do you want to make this edit?", "Do you want to create this file?", …).

### Where a fix goes, in dependency order

1. **Air Web client (the actual gap; not in this repo or install).** Render a permission-mode picker driven by the ACP `SessionModeState` already produced by `toPermissionModeState`, mirroring the shipped model-selector pattern; add an `ai/select-permission-mode` action id alongside `ai/select-model`.
2. **`fleet.ship.desktop.air.AirShipLauncherKt`** — flip `ShowAutonomySettingsAttr` to `true` for the Air profile. One-line change; the attribute and its `true` default already exist.
3. **Default-mode review.** `AgentModelConfiguration.Agent.PermissionMode.isJcpDefault` is the intended mechanism. It is *remotely* configured (`agent-model-configuration.json`, fetched from `https://plugins.jetbrains.com/fleet-parts`) or overridden by the settings key `ai.custom.agent.model.configuration` — so this is likely a server-side data change, not code.
4. **No backend work is required.** The enums, the `*PermissionsUpdater` family, `acp/set-session-mode`, `acp/set-brave-mode`, and the FUS schema are all already in place.
